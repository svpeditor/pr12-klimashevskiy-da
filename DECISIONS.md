# DECISIONS.md

## Вариант

Номер варианта: 4 (две последние цифры зачетки 25Т0859: 59 mod 8 + 1 = 4).

Изменяемый аспект: порог крупной сделки, параметр 25.
Как применен параметр: суммы продаж в файле в рублях (45 000 - 240 000), и сделка на 25 рублей крупной
быть не может. Поэтому 25 прочитано в тысячах рублей, как суммы обычно пишут в отчетах по продажам.
В базовом задании я взял порог 100 000, по варианту он стал 25 000.
Правило, которое реализовано: сделка крупная, если ее сумма не меньше 25 000 рублей. 24 999.99 - не крупная,
25 000 - уже крупная.

Где сосредоточено: константа SalesAnalyticsService.LARGE_DEAL_MIN = 25000. Ее использует метод isLarge,
а через него largeSales, и она же передается как min в topSales при выводе топа крупных сделок.

## Решение 1. Сортировка через один Comparator с двумя полями

Формулировка: в сервисе есть константа BY_AMOUNT_DESC_THEN_ID = Comparator.comparingDouble(Sale::amount)
.reversed().thenComparing(Sale::id). topSales строится как filter, затем sorted(BY_AMOUNT_DESC_THEN_ID),
затем limit и toList.

Альтернатива: сортировать вручную обменом элементов или сравнивать только по сумме.

Обоснование: ручная сортировка длиннее и меняет список, а сортировка только по сумме дает случайный порядок
для одинаковых сумм. Со вторым полем id порядок всегда один: S2 и S5 по 92 000 идут как S2, S5. Comparator
вынесен в константу, чтобы им можно было пользоваться и в других методах.

## Решение 2. Каждый метод возвращает новый результат и не меняет входной список

Формулировка: topSales и largeSales собирают результат через toList, totalsByManager через
groupingBy(Sale::manager, TreeMap::new, summingDouble(Sale::amount)), maxSale возвращает Optional<Sale>,
averageByRegion возвращает 0, если продаж в регионе нет.

Альтернатива: собирать результат в заранее созданный ArrayList внутри forEach, а при отсутствии продаж
возвращать null.

Обоснование: внешний список внутри stream - это побочный эффект, который запрещен правилами. null при пустом
списке легко забыть проверить, а Optional прямо показывает, что результата может не быть. TreeMap выбран,
чтобы менеджеры выводились по алфавиту. В SelfCheck source unchanged проверяет, что входной список
после всех методов равен своей копии, а immutable input - что методы работают и с неизменяемым списком.

## Переписанный цикл

Метод averageByRegion сначала был написан циклом (коммит базового задания):

    double sum = 0;
    int n = 0;
    for (Sale s : sales) {
        if (s.region().equals(region)) {
            sum += s.amount();
            n++;
        }
    }
    return n == 0 ? 0.0 : sum / n;

Потом он переписан через Stream API (отдельный коммит):

    return sales.stream()
            .filter(s -> s.region().equals(region))
            .mapToDouble(Sale::amount)
            .average()
            .orElse(0.0);

Stream-версия читается как описание шагов: отобрать регион, взять суммы, посчитать среднее. Не нужны два
счетчика и отдельная проверка деления на ноль, пустой случай закрывает orElse(0.0). Для такой простой
агрегации stream читается лучше, а разбор файла в SelfCheck я оставил циклом, потому что там на каждой
строке свой try-catch и вывод ошибки, и в stream это читалось бы хуже.

## Результаты граничных проверок

- типовое значение: data/sample.csv - топ-3 крупных S3, S1, S2; максимум S3 240 000; Ivanov 390 000;
  среднее Moscow 195 000
- граница порога по варианту: 24 999.99 не крупная, 25 000 крупная; topSales с min = 150 000 включает S1 ровно 150 000
- граница limit: limit 0 - пустой список, limit больше числа подходящих - все подходящие, limit -1 - ошибка
- пустое значение: maxSale пустого списка - Optional.empty, среднее по неизвестному региону и пустому списку - 0,

- неверный формат: отрицательная сумма, сумма abc, строка из 3 полей - строка файла пропущена с причиной
- повтор: повторный id S1 в файле пропущен; одинаковые суммы S2 и S5 упорядочены по id

Все проверки есть в SelfCheck (25 PASS). Файл data/boundaries.csv: загружено 6 продаж, пропущено 5 строк,

## Собственные формулировки

### Какая проверка защищает от наиболее вероятной ошибки входных данных

Самая вероятная ошибка в выгрузке продаж - неверная сумма (минус, текст вместо числа) или пустой менеджер.
Ее ловит компактный конструктор записи Sale: отрицательная сумма, пустой id, менеджер или регион дают
IllegalArgumentException, и такая продажа не попадает в список. Текст вместо числа ловит разбор строки
в SelfCheck. Поэтому методы сервиса работают только с корректными продажами и сами ничего не проверяют,
кроме limit.

### Какой метод или класс содержит ключевое бизнес-правило и почему

Ключевое правило варианта - что считать крупной сделкой. Оно в методе isLarge и константе LARGE_DEAL_MIN
класса SalesAnalyticsService. isLarge - отдельный метод, чтобы его можно было передать в filter как
this::isLarge и чтобы порог был в одном месте, а не повторялся в нескольких лямбдах.

### Как Activity-диаграмма отражает участок кода

Диаграмма показывает topSales. "Сформировать stream" - sales.stream(), блок A1 - filter(s -> s.amount() >= min),
"Преобразовать или отсортировать" - sorted(BY_AMOUNT_DESC_THEN_ID), терминальная операция - limit(limit).toList().
Ромб "Результат найден" в коде отдельного if не имеет: если ничего не прошло фильтр, toList вернет пустой
список, а для maxSale max вернет Optional.empty.

### Какое изменение требования затронет минимум классов

Изменение порога крупной сделки меняет одну константу LARGE_DEAL_MIN. Изменение второго поля сортировки
(например, менеджер вместо id) меняет одну строку в BY_AMOUNT_DESC_THEN_ID. Sale и SelfCheck при этом
не меняются, кроме явных проверок варианта на 24 999.99 и 25 000.

## Фрагмент кода для анализа

List<Sale> result = new ArrayList<>(); sales.stream().filter(this::isLarge).forEach(result::add); меняет
внешний список изнутри stream. Это побочный эффект, который запрещен правилами работы: результат зависит
от состояния переменной снаружи, а при parallelStream несколько потоков будут добавлять в обычный ArrayList
одновременно и могут потерять элементы. В моем проекте метод largeSales написан как
sales.stream().filter(this::isLarge).toList(), stream сам собирает новый список.
